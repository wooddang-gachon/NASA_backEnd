## 📌 3. 설계 패턴

### 3-1. Repository Pattern
- Service ↔ Repository 계층 완전 분리
- Prisma ORM 의존성을 Repository 계층으로 100% 격리
- Service는 순수 비즈니스 로직만 담당
- Controller에서 Prisma 직접 호출 0건

### 3-2. Exception Translation Pattern
- 외부 AI 서버 에러 → `AiServerError` (503)
- 소셜 인증 실패 → `BadGatewayError` (502)
- 사용자 미존재 → `UserNotFoundError` (404)
- 연료 부족 → `BadRequestError` (400, INSUFFICIENT_FUEL)
- 중복 가입 → `ConflictError` (409)

### 3-3. Dependency Injection (TypeDI)
- `@Service()` 데코레이터로 IoC 컨테이너에 등록
- `@Inject()` 프로퍼티 주입
- 테스트 환경에서 `MockAiService`, `MockAuthService` 동적 교체
- `src/loaders/ioc.ts`에서 TSOA ↔ TypeDI 바인딩

### 3-4. No Auto-Create 원칙
- 모든 Service에서 사용자 존재 여부 선검증
- 미존재 시 `UserNotFoundError (404)` 예외 발생
- 리소스 자동 생성 절대 금지

## 📌 4. 디렉토리 구조

```
src/
├── api/
│   ├── middlewares/    # JWT 인증, 전역 에러 핸들러
│   └── routes/        # TSOA 컨트롤러 (7개)
├── config/            # 환경 변수 설정 (.env 매핑)
├── constants/         # 게이미피케이션 상수 중앙 관리
├── dto/               # Request/Response DTO (9개)
├── errors/            # 커스텀 에러 클래스 (9개)
├── interfaces/        # 도메인 인터페이스 & Enum (10개)
├── jobs/              # Cron 스케줄러 (2개 작업)
├── loaders/           # Express, Prisma, Logger, Swagger, IoC 초기화
├── mappers/           # DB Entity ↔ DTO 변환 (5개)
├── repositories/      # 데이터 접근 계층 (7개 + models/)
│   └── models/        # DB 반환 모델 타입 정의
├── services/          # 비즈니스 로직 (9개 + mocks/)
│   └── mocks/         # MockAiService, MockAuthService
├── utils/             # 유틸리티
│   └── food/          # 음식 토큰화, 키워드 정제, 객체 탐지
└── build/             # TSOA 자동 생성 (routes.ts, swagger.json)
```

```
          │ /v1/vision/analyze-food   │

```

### AI 서버 통신 규격
- 인증: `X-Internal-Api-Key` 헤더
- 이미지 전송: Base64 인코딩 (512x512 JPEG, 품질 60%)
- 에러 처리: 통신 실패 시 `AiServerError (503)` 변환

### Firebase Cloud Messaging
- 디바이스 토큰 등록/갱신 (Upsert)
- 대량 발송 시 500개 단위 청크 분할 (`sendEachForMulticast`)
- 서비스 계정 키 파일 필요 (`firebase-service-account.json`)

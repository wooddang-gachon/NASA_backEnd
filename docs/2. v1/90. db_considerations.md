# TAMMY v3 데이터베이스 설계 고려사항 및 의사결정 기록 (Database Considerations & Decision Log)

본 문서는 TAMMY v3 백엔드 개발 시 MySQL 데이터베이스 설계 및 쿼리 최적화 과정에서 성능, 동시성, 무결성을 보장하기 위해 수립된 핵심 가이드라인 및 설계 결정 이력(Decision Log)을 정리합니다.

---

## 1. 영양 마스터 정규화 및 캐싱 (Food Master & Meal Caching)

### 1.1 표준 음식 마스터 DB (`foods`) 분리
- **이슈**: 사용자의 식사 이력에 음식 영양성분이 텍스트로 중복 적재되어 검색 자동완성이나 AI 스캔 매핑이 불가능함.
- **해결 방안**:
  - `foods` 표준 음식 마스터 테이블을 독립 신설하여 음식명(`name UNIQUE`), 표준 1회 제공량(`standard_serving_g`), 5대 영양소 마스터 정보 구축.
  - `meal_items`에 `food_id INT NULL` FK 및 실제 섭취 분량(`intake_gram`)을 추가하여 섭취 비율 정산 지원.
  - 마스터 DB에 없는 커스텀 음식도 `custom_food_name`으로 수동 등록 가능하도록 유연성 확보.

### 1.2 헬스케어 1:N 분할 및 캐싱 (meals & meal_items)
- 매번 자식 `meal_items`의 대량 레코드를 `SUM` 연산하는 부하를 방지하기 위해 부모 `meals` 테이블에 **5대 영양소 캐시 컬럼**(`total_calories_kcal`, `total_carbohydrate_g`, `total_protein_g`, `total_fat_g`, `vitamin_percent`, `mineral_percent`)을 역정규화로 유지.

### 1.3 다중 음식 사진 분리 및 수치 우선 로딩 (Multi-Image 1:N & Lazy Loading)
- **이슈**: 사용자가 식사 1번에 식판 사진, 디저트 사진 등 여러 장의 사진(1:N)을 등록할 수 있는 요구사항과, 식사 목록 조회 시 가벼운 수치/영양소 텍스트 데이터를 0.1초 만에 우선 로딩한 후 이미지는 늦게(Lazy Loading) 렌더링해야 하는 프론트엔드 최적화 필요성 대두.
- **해결 방안**:
  - `meals` 테이블에서 단일 `image_url` 필드를 제거하고, `meal_images` 독립 테이블(`meal_id` FK 참조)을 1:N 관계 구조로 신설.
  - 목록 조회 시 부모 `meals`의 수치 텍스트만 초고속 쿼리로 1차 렌더링하고, 자식 `meal_images`는 클라이언트 뷰포트 교차(Intersection Observer/FastImage) 시 비동기로 늦게 지연 로딩(Lazy Loading)하도록 아키텍처 수립.

## 2. 대화 데이터 무결성 및 영구 연동 (Memory & Archive Lineage)

### 2.1 기억 캡슐(`long_term_memories`)의 영구 백업 연동 아키텍처
- `long_term_memories`의 원본 대화 외래키를 절대 삭제되지 않는 불변(Append-Only) 테이블인 **`chat_message_archives.id` (`chat_message_archive_id`)에 연동**.
- 사용자가 채팅방에서 라이브 메시지를 삭제하더라도, AI 기억 캡슐의 추출 근거 데이터 무결성이 평생 영구 보존됨.

## 3. 조회 성능 최적화 (Index 설계 가이드)

### 3.1 시계열 대화 및 로그 복합 인덱스 (Composite Index)
- `chat_messages`, `chat_message_archives`, `user_body_logs`, `meals`, `exercise_logs`, `water_logs`, `emotion_logs`, `activity_logs`에 `(user_id, 날짜/생성일 DESC)` 복합 인덱스 적용.

### 3.2 고도화 쿼리 전용 복합 인덱스
- **음식 검색 자동완성 쿼리 (`foods`)**: `WHERE name LIKE ?` 초고속 조회를 위한 `foods.name` UNIQUE 인덱스 활용.
- **모바일 증분 동기화 커서 쿼리 (`exercise_logs`)**: `INDEX idx_user_exercise_sync (user_id, id ASC)` 복합 인덱스 반영.
- **선제적 안부 톡 대기 쿼리 (`proactive_triggers`)**: `INDEX idx_user_pending_trigger (user_id, status, created_at DESC)` 복합 인덱스 반영.
- **식사 종류별 검색 쿼리 (`meals`)**: `INDEX idx_user_meal_type (user_id, meal_type, registered_at DESC)` 복합 인덱스 반영.
- **클릭스트림 디버깅 조회가 (`user_action_logs`)**: `INDEX idx_action_user_created (user_id, created_at DESC)` 및 `INDEX idx_action_screen (screen_name, created_at DESC)` 인덱스로 장애 발생 직전 클릭 행동 추적.
- **타미 성장 이력 조회가 (`tammy_status_logs`)**: `INDEX idx_tammy_log_user_created (user_id, created_at DESC)` 인덱스로 레벨업 및 지수 변화 그래프 이력 조회를 최적화.

## 4. 원장 및 이벤트 로그 동시 갱신 트랜잭션 (Ledger & Audit Trail Pattern)

### 4.1 `tammy_statuses` 원장 ↔ `tammy_status_logs` 변동 이중화
- **원자적 트랜잭션 (Atomic Transaction)**: 경험치나 4대 지수가 상승할 때, `tammy_statuses` 원장 테이블을 갱신함과 동시에 `tammy_status_logs` 테이블에 변동 내역(`delta_exp`, `delta_activity` 등) 및 변동 직후 스냅샷(`snapshot_level`, `snapshot_total_exp`)을 동일 DB 트랜잭션 내에서 처리하여 원장과 로그 간 이격(Discrepancy)을 완전 차단.
- **30일 만료 배치 파기 (30-Day Retention Policy)**: `tammy_status_logs` 데이터는 최신 30일간의 그래프 차트 렌더링 및 이력 조회에 사용되며, 30일이 경과한 오래된 로그 데이터는 매일 정해진 시각에 만료 배치(Cron Job)를 실행하여 자동 삭제 정리함으로써 데이터베이스 크기 오버헤드를 차단.

## 4. 디버깅 및 분석 로그 수집 가이드라인 (Clickstream Logging)

### 4.1 `user_action_logs` 처리 최적화
- **비동기 큐 (Asynchronous Queue) 및 배치 인서트**: 클릭 로그 수집 시 메인 대화/식단 API 응답 지연을 유발하지 않도록, 모바일 앱에서 10~20개 이벤트를 묶어서 비동기 배치(`POST /api/analytics/action-logs`)로 보낼 수 있도록 지원.
- **주기적 아카이빙/보관 주기**: 디버깅 용도 로그이므로 90일이 경과한 오래된 클릭 로그는 만료 배치(Cron)를 통해 자동 이관/삭제 처리 조치.

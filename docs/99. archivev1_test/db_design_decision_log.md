# TAMMY Database Design Decision Log (v3)

본 문서는 TAMMY v3 서비스의 데이터베이스 설계 과정에서 도출된 핵심 설계 의사결정과 `db_verifier` 에이전트 진단 기반의 하이브리드 고도화 반영 내역을 기록한 로그입니다.

---

## 1. 행성(Planets) 테이블 설계 방식

### 1.1 고민 사항
우주여행 행성들의 메타데이터를 마스터 테이블로 관리할 때, 어떤 구조로 모델링할 것인가?
- **대안 A**: 단일 마스터 테이블 (Single Table)에 모든 타입의 컬럼을 모아둠.
- **대안 B**: 부모 테이블과 자식 테이블을 쪼개어 1:1 관계로 연결하는 상속(Class Table Inheritance) 구조로 설계.

### 1.2 최종 결정 및 이유
- **결정**: **상속 테이블(Class Table) 구조 적용 및 하이브리드 무결성 수정**
- **이유**: 운동, 영양 등 행성별 도메인에 따라 관리해야 할 고유 데이터가 다르고 향후 신규 행성 테마 추가 시 스키마 확장성이 더 중요하다고 판단했기 때문입니다.
- **하이브리드 고도화 보완**: 
  - [오류 해결] 기존 DDL 상에서 부모 `planets.planet_type`은 ENUM이나 자식 테이블들의 생성 컬럼이 `VARCHAR`로 지정되어 MySQL 빌드가 불가능한 치명적 결함(MySQL ERROR 3780)을 발견했습니다. 
  - 이를 해결하기 위해 자식 테이블들의 가상 생성 컬럼 타입을 부모와 완벽히 일치하는 `ENUM` 타입으로 수정하여 외래 키 제약 조건이 정상적으로 바인딩되도록 조치했습니다.

## 2. 헬스케어 로그 정규화 및 1:N 분할

### 2.1 신체 스펙(키, 몸무게) 데이터
- **결정**: `users`에서 신체 스펙을 제거하고, 1:N 관계의 신체 스펙 히스토리 이력 테이블인 **`user_body_logs`**로 분리하여 시계열 데이터 유실을 방지했습니다.

### 2.2 운동 기록 구조
- **결정**: 운동 마스터 정보를 지닌 **`exercises`** 테이블을 신설하고, `exercise_logs`는 이를 외래 키로 참조하도록 정규화했습니다.

### 2.3 식단 기록 구조
- **결정**: 식사 이벤트를 담당하는 **`meals`** 테이블과, 식사 내 포함된 개별 음식들의 영양성분을 각각 저장하는 **`meal_items`** 테이블로 1:N 쪼개기를 실행했습니다.
- **하이브리드 고도화 보완**: 하루 권장량 및 영양 집계 시 매번 자식 `meal_items`의 대량 레코드를 `SUM` 연산하는 부하를 방지하기 위해, 부모인 `meals` 테이블에 당일 섭취 총합을 보존하는 **반정규화 영양 캐시 컬럼**(`total_calories_kcal`, `total_carbohydrate_g` 등)을 추가하여 조회 속도를 극대화했습니다.

## 3. 채팅 메시지 및 수정 이력 구조

### 3.1 보낸사람 / 받는사람 구분 방식
- **결정**: 단순하게 발신자만 나타내는 **`sender ENUM('USER', 'TAMMY')`** 구조 유지. (1:1 에이전트 구조상 JOIN이 불필요하여 쿼리가 가장 빠름)

### 3.2 메시지 수정 이력
- **결정**: 메인 메시지(`chat_messages`)와 수정 이력 테이블(**`chat_message_edits`**)을 1:N 분리. 메인 메시지에는 수정 여부 플래그(`is_edited`)를 두어 실시간 조회를 최적화하고, 원본 데이터 조회 시에만 이력 테이블을 활용합니다.

## 4. 타임라인 및 에이전트 반응 시스템 고도화

### 4.1 통합 활동 로그 (activity_logs)의 JSON 역정규화
- **고민 사항**: 사용자가 일 단위로 "운동함", "물 마심", "식사함", "감정 변화" 등을 시간 순서로 쭉 나열하는 타임라인 피드를 그릴 때, 흩어진 5개 로그 테이블을 각자 조회하면 성능이 저하됨.
- **기존안**: 5개 자식 테이블의 외래 키(FK)를 널러블하게 지닌 통합 테이블 설계.
- **한계점**: 5개 테이블을 매번 LEFT JOIN하여 데이터를 조각조각 가져오는 조인 오버헤드가 크고 신규 로그 종류 추가 시 DDL 수정이 수반됨.
- **최종 결정 (하이브리드 반영)**: 개별 FK 연결을 모두 걷어내고, 상세 이력 정보를 JSON 타입의 **`activity_details`** 컬럼에 **스냅샷 스키마로 직접 적재하는 역정규화 기법을 채택**했습니다. 단일 테이블 초고속 조회를 가능하게 하고 스키마 유연성을 확보했습니다.

### 4.2 능동형 에이전트 반응 (proactive_triggers) 도입
- **결정**: 감정, 수분 부족, 운동 부족 등 다양한 원인으로 발동되는 타미의 모든 선제적 리마인더 및 안부 대화 이력을 일관되게 제어하는 **`proactive_triggers`** 테이블을 별도로 구성했습니다.

---

## 5. 네이밍 컨벤션 표준화 및 인덱스 정비

### 5.1 네이밍 컨벤션 표준화
- 복수형 테이블명 일관성을 위해 `tammy_status`를 **`tammy_statuses`**로 변경했습니다.
- `chat_message_edits.chat_message_id` 등 외래 키 명칭 정교화.
- 칼로리, 신장, 체중, 영양소 등의 컬럼에 물리 단위 접미사(`_cm`, `_kg`, `_g`, `_kcal`)를 명시하여 프론트/백엔드 통신 및 개발상 혼선과 실수를 사전에 차단했습니다.

### 5.2 정렬 복합 인덱스(Composite Index) 선제 반영
- 유저별로 최근 타임라인, 메시지, 로그 이력을 내림차순(DESC) 조회하는 쿼리가 잦으므로, 모든 시계열 로그성 테이블들에 **`(user_id, 날짜/생성일 DESC)`** 형태의 복합 인덱스를 선제적으로 정의했습니다.
- 중복되는 `long_term_memories`의 외래키 단일 인덱스는 복합 유니크 키(`uq_user_category`)로 대체하여 쓰기 오버헤드를 줄였습니다.
